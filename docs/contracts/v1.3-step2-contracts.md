### 1.4 Editor draft (workspace v2 focus replacement)

~~~ts
const DraftTargetSuggestion = z.object({
  kind: z.literal("suggestion"), suggestionId: z.string().regex(/^sug-[0-9]{3}$/),
}).strict();
const DraftTargetBullet = z.object({
  kind: z.literal("bullet"), factId: Key,
}).strict();

export const Step2DraftOperationV1 = z.discriminatedUnion("op", [
  z.object({ op: z.literal("add"), operationId: Id, suggestionId: z.string().regex(/^sug-[0-9]{3}$/),
    roleId: Key, editedText: z.string().max(2000).nullable() }).strict(),
  z.object({ op: z.literal("replace"), operationId: Id, targetFactId: Key, roleId: Key,
    suggestionId: z.string().regex(/^sug-[0-9]{3}$/).nullable(),
    editedText: z.string().min(1).max(2000).nullable() }).strict(),
  z.object({ op: z.literal("exclude"), operationId: Id, targetFactId: Key }).strict(),
  z.object({ op: z.literal("edit"), operationId: Id,
    target: z.discriminatedUnion("kind", [DraftTargetSuggestion, DraftTargetBullet]),
    text: z.string().min(1).max(2000) }).strict(),
]);
export type Step2DraftOperationV1 = z.infer<typeof Step2DraftOperationV1>;

export const Step2DraftV1 = z.object({
  schemaVersion: z.literal(STEP2_SCHEMA_VERSIONS.draft),
  planId: Id,
  planHash: Hash,
  summaryText: z.string().max(4000),
  summarySource: z.enum(["master", "angle-1", "angle-2", "edited"]),
  operations: z.array(Step2DraftOperationV1).max(50),
}).strict();
export type Step2DraftV1 = z.infer<typeof Step2DraftV1>;
~~~

Semantic rules: `operationId` unique within the draft; array order is
display/apply order (drag reorder rewrites order, no `move` op);
`add` with an `editedText` equals add-then-edit atomically; `replace`
carries exactly one of `suggestionId`/`editedText` (exclusive-or,
validated by refinement); repeated Use/drop of the same usable
suggestion is idempotent — W collapses a second `add` for the same
`suggestionId`+`roleId` to the existing `operationId` instead of
appending; `exclude` of an already-excluded bullet is a no-op; undo
removes the operation (source facts are never mutated). `edit` on a
`suggestion` target applies to the added instance; `edit` on a
`bullet` target rewords a master bullet in place (still attributed to
its role). A `replace` naming a `suggestionId` requires that
suggestion `usable` in the bound plan; unusable suggestions and gap
priorities can never enter an `add`/`replace`.

## 2. Identities, hashes, and digests

All digests are lowercase hex SHA-256 over UTF-8 bytes, computed with
`canonicalJson` (key-sorted, no whitespace) or the stated raw bytes.
Implement in `src/tailoring/step2policy.ts` (hashes live in tailoring
per the domain purity guard; schemas stay in `src/domain/step2.ts`):

| Digest | Definition |
|---|---|
| `evidenceHash` | `SHA256(canonicalJson({profileVersionId, payloadHash, approved: [{factId, statement, employmentId}] sorted by factId}))`; approved = `verification = APPROVED` rows for the version |
| `bindingHash` | `SHA256(canonicalJson(IntakeBindingV1))` |
| `priorityId` | the existing `phraseIdFor({extractionId, jdHash, startByte, endByte, text})` from `src/tailoring/requestsV3.ts` — reused verbatim, never reimplemented; `s2a-schemas` pins byte-equality on fixtures |
| `masterProjectionHash` | `SHA256(canonicalJson(masterBulletsByRole(payload)))` per `STEP2_MASTER_PROJECTION` (`step2-master-bullets/1`): approved achievements in payload order grouped by `employmentId` (unlinked achievements under role key `""`), each `{factId, text}` with `text = canonicalText(achievement.text)` |
| `planHash` | `SHA256(canonicalJson(PreparationPlanV1))` |
| `draftHash` | `SHA256(canonicalJson({planId, planHash, summaryText, summarySource, operations}))` |
| `segmentTextHash` | `SHA256` of exact submitted segment bytes; `segmentNormalizedHash` covers `canonicalText` bytes |
| `prepareOperationHash` | `SHA256(canonicalJson({jobId, operationId, observedRowVersion, profileId}))` — idempotency identity for POST preparation |
| `prepare` idempotency key | `prepare:{jobId}:{preparationId}:{extractionId}` — per supersession cycle: retries reuse the key, a new extraction cycle mints a new work item while the terminal history stays untouched (S2-B amendment 2026-09-17; the S2-A two-part key collided across cycles on one row) |
| `v13_one_live_prepare` | partial unique index `work_items(job_id)` where `kind = 'PREPARE' AND state IN ('QUEUED','RUNNING')` |

`masterBulletsByRole` is total and deterministic: it never calls a
provider, never invents bullets, and is byte-stable for a fixed
payload. The editor's "existing master bullets by role" is exactly
this projection over the captured version payload.

## 3. SQL and Drizzle specification (migration 0009)

S2-B implements `drizzle/0009_step2_preparation.sql` from this
section plus the exact Drizzle mirror in `src/db/schema/step2.ts`.
Conventions mirror 0008: `TEXT` ids, `CHECK` ranges/enums, named

### 3.1 `step2_preparations` — one row per intake-bound job

~~~sql
CREATE TABLE step2_preparations (
  id TEXT PRIMARY KEY,
  intake_item_id TEXT UNIQUE REFERENCES intake_items(id),
  job_id TEXT UNIQUE REFERENCES jobs(id),
  batch_id TEXT REFERENCES intake_batches(id),
  profile_id TEXT NOT NULL REFERENCES candidate_profiles(id),
  profile_version_id TEXT NOT NULL REFERENCES candidate_profile_versions(id),
  extraction_id TEXT REFERENCES job_extractions(id),
  profile_payload_hash TEXT NOT NULL,
  evidence_hash TEXT NOT NULL,
  master_source_id TEXT REFERENCES candidate_sources(id),
  binding_json TEXT NOT NULL,
  state TEXT NOT NULL DEFAULT 'PENDING'
    CONSTRAINT s2_prep_state CHECK(state IN ('PENDING','QUEUED','RUNNING','SUCCEEDED','FAILED')),
  work_item_id TEXT UNIQUE REFERENCES work_items(id),
  accepted_plan_id TEXT REFERENCES step2_plans(id),
  last_operation_id TEXT,
  last_operation_hash TEXT,
  failure_json TEXT,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
  CONSTRAINT s2_prep_hashes CHECK(
    profile_payload_hash GLOB '[0-9a-f]*' AND length(profile_payload_hash) = 64 AND
    evidence_hash GLOB '[0-9a-f]*' AND length(evidence_hash) = 64),
  CONSTRAINT s2_prep_binding_bytes CHECK(length(binding_json) <= 8192),
  CONSTRAINT s2_prep_failure_bytes CHECK(failure_json IS NULL OR length(failure_json) <= 8192),
  CONSTRAINT s2_prep_op_pair CHECK(
    (last_operation_id IS NULL) = (last_operation_hash IS NULL)),
  CONSTRAINT s2_prep_accepted_state CHECK(
    accepted_plan_id IS NULL OR state IN ('SUCCEEDED','QUEUED','RUNNING','FAILED')),
  CONSTRAINT s2_prep_times CHECK(
    strftime('%Y-%m-%dT%H:%M:%fZ', created_at) IS NOT NULL AND
    strftime('%Y-%m-%dT%H:%M:%fZ', updated_at) IS NOT NULL)
);
CREATE INDEX s2_preparations_job_id ON step2_preparations(job_id);
CREATE INDEX s2_preparations_batch_id ON step2_preparations(batch_id);
CREATE INDEX s2_preparations_state ON step2_preparations(state);
~~~

Row lifecycle: inserted at intake acceptance with `job_id` and
`extraction_id` NULL (`PENDING`); the extraction worker links both and
schedules (§8.2). Legacy rows are inserted by the explicit command
with `job_id` set and `intake_item_id`/`batch_id` NULL (§8.5).
`UNIQUE` on nullable columns is partial by nature (SQLite treats
NULLs as distinct). `s2_prep_accepted_state` permits a retained
accepted plan across a supersession cycle while never accepting from
`PENDING`.

Triggers:

- `s2_prep_no_delete BEFORE DELETE`: `RAISE(ABORT,
  'PREPARATION_IMMUTABLE')`. Preparation rows are never deleted;
  reset follows the database-rebuild path.
- `s2_prep_accepted_forward BEFORE UPDATE OF accepted_plan_id WHEN
  NEW.accepted_plan_id IS NOT NULL`: abort `PLAN_POINTER_BACKWARD`
  unless the new plan belongs to this preparation with a greater
  `plan_seq` than the old pointer (or the old pointer is NULL).
- `s2_prep_binding_locked BEFORE UPDATE OF intake_item_id, batch_id,
  profile_id, profile_version_id, profile_payload_hash, evidence_hash,
  master_source_id, binding_json`: abort `BINDING_IMMUTABLE`. The
  captured binding never changes. Exactly one binding per row,
  written once: the explicit legacy/missing-profile command binds at
  row creation; a JD supersession keeps the profile binding and only
  relinks `extraction_id` (see §8.6).

### 3.2 `step2_plans` — append-only accepted-plan history

~~~sql
CREATE TABLE step2_plans (
  id TEXT PRIMARY KEY,
  preparation_id TEXT NOT NULL REFERENCES step2_preparations(id),
  plan_seq INTEGER NOT NULL,
  plan_json TEXT NOT NULL,
  plan_hash TEXT NOT NULL,
  provider_id TEXT NOT NULL,
  model TEXT,
  prompt_version TEXT NOT NULL,
  proposal_schema_version TEXT NOT NULL,
  claims_policy_version TEXT NOT NULL,
  input_hash TEXT NOT NULL,
  proposal_hash TEXT NOT NULL,
  attempt_id TEXT NOT NULL REFERENCES work_attempts(id),
  validation_json TEXT NOT NULL,
  supersedes_plan_id TEXT REFERENCES step2_plans(id),
  created_at TEXT NOT NULL,
  UNIQUE(preparation_id, plan_seq),
  CONSTRAINT s2_plan_seq CHECK(plan_seq >= 1),
  CONSTRAINT s2_plan_bytes CHECK(length(plan_json) <= 65536 AND length(validation_json) <= 65536),
  CONSTRAINT s2_plan_hashes CHECK(
    plan_hash GLOB '[0-9a-f]*' AND length(plan_hash) = 64 AND
    input_hash GLOB '[0-9a-f]*' AND length(input_hash) = 64 AND
    proposal_hash GLOB '[0-9a-f]*' AND length(proposal_hash) = 64),
  CONSTRAINT s2_plan_versions CHECK(
    prompt_version = 'prepare-prompt/v1' AND
    proposal_schema_version = 'preparation-proposal/v1' AND
    claims_policy_version = 'step2-claims/1'),
  CONSTRAINT s2_plan_time CHECK(strftime('%Y-%m-%dT%H:%M:%fZ', created_at) IS NOT NULL)
);
CREATE INDEX s2_plans_preparation_id ON step2_plans(preparation_id);
CREATE UNIQUE INDEX s2_plans_hash ON step2_plans(preparation_id, plan_hash);
~~~

Triggers: `s2_plan_no_update` / `s2_plan_no_delete` abort
`PLAN_IMMUTABLE`; `s2_plan_owner BEFORE INSERT` aborts
`PLAN_PREPARATION_MISMATCH` unless `supersedes_plan_id` is NULL or
names a plan of the same preparation with a smaller `plan_seq`.
`validation_json` is the worker's per-item proposal validation record
(`usable` flags with reasons, §7.2), not the draft verdict. Its
versioned shape is `PlanValidationV1`

### 4.1 Transaction P — explicit preparation schedule

P runs `POST .../tailoring/preparation`. Compute hashes and parse
payloads outside the transaction. `BEGIN IMMEDIATE`:

1. Load job; 404 when missing. Load preparation row by `job_id`
   (nullable) and resolve the effective binding: existing row →
   captured binding; no row → require `profileId`, resolve that
   profile's ACTIVE version at this instant (the version shown to the
   user, §8.5).
2. Idempotency: when a row exists with `last_operation_id =
   operationId`: identical `prepareOperationHash` → 200 replay, zero
   writes; different → 409 `IDEMPOTENCY_MISMATCH`, zero writes.
3. Job CAS: `jobs.row_version = observedRowVersion`, else 409
   `JOB_CONFLICT`. Busy: preparation state in `QUEUED`/`RUNNING` →
   409 `PREPARATION_BUSY`.
4. Readiness, in order: no usable profile binding → 422
   `PROFILE_NOT_READY`; no retained JD on the active extraction → 422
   `JD_NOT_READY`; no provider key for the active provider → 422
   `PROVIDER_NOT_READY`. Rejected jobs → 409 (existing reopen rule).
5. Supersession check: when a row exists with an accepted plan whose
   `extraction_id` ≠ active extraction, relink `extraction_id` to the
   active extraction (same row, §8.6) and continue as a new cycle;
   `accepted_plan_id` is retained until the new plan publishes.
6. Create-or-reuse: no row → insert the preparation row bound to
   the resolved profile version (`PENDING`, `intake_item_id`/
   `batch_id` NULL for legacy jobs, `job_id` set). A legacy row's
   binding is written once at creation and is immutable thereafter.

7. Insert the PREPARE work item (`prepare:{jobId}:{preparationId}:{extractionId}`
   idempotency key, `PreparePayloadV1`; `maxAttempts = 3`), set row
   state `QUEUED`, `work_item_id`, `last_operation_id/hash`, clear
   `failure_json`. CAS the job `row_version` + 1 (preparation
   commands bump the job version exactly like G/R, so concurrent
   reviewers observe the change; board status is untouched).
8. Commit → 202. Any failure rolls back all writes, including a new
   preparation row. No provider call, no snapshot creation, no
   `generation_requests`/`resume_versions`/`resume_reviews`/
   `applications` write (ΔQ1 = 0, ΔQ4 = 0 — S2B2 probes).

### 4.2 Transaction PR — preparation retry (attempt-specific)

PR mirrors R: `BEGIN IMMEDIATE`; resolve the owned preparation and
the observed attempt. Replay precedes every check: when a later
attempt exists on the work item, or the work item is already
`QUEUED`/`RUNNING`, return 200 with zero writes. Otherwise require:
terminal retryable failure on the observed attempt (retryable =
all preparation codes except `INPUT_STALE` and
`PROFILE_UNAVAILABLE`), current binding/extraction, job CAS, and no
other live run for the job; then requeue through the existing
`requeueWorkItem` primitive (budget extends, numbering preserved),
set row state `QUEUED`, clear `failure_json`. An earlier observed
attempt never requeues a later failure. Statuses per the §4 table;
`RETRY_NOT_ALLOWED` (422) covers latest-successful, non-retryable,
and legacy/absent-preparation cases.

### 4.3 Intake batch read extension (additive)

`GET /api/intake/batches/:id` keeps its exact current shape and adds
per item:

~~~ts

  state: z.enum(["ABSENT","PENDING","QUEUED","RUNNING","SUCCEEDED","FAILED"]),
~~~

## 5. CAS, idempotency, and polling

- Workspace ETag keeps the exact B scheme `"tw:{jobId}:{revision}"`
  for both v1 and v2 bodies: absent → 428, malformed/wildcard/list →
  400, wrong job/revision → 412 `WORKSPACE_CONFLICT`. The response
  carries the stored version's schema; clients branch on
  `schemaVersion`.
- Job CAS keeps `observedRowVersion` (409 `JOB_CONFLICT`),
  independent of workspace ETag. P/PR bump `jobs.row_version`;
  preparation state never moves board status.
- P idempotency is (`operationId`, `prepareOperationHash`) stored on
  the preparation row; PR replay is attempt-identity based like R.
  Same-id/changed-bytes → 409 `IDEMPOTENCY_MISMATCH` in both.
- Polling reuses the Step 3 cadence: 2 s visible / 10 s hidden,
  stopping at terminal preparation states. Browser clocks write
  nothing. Batch diagnostics poll the batch GET, never a mutation.

## 6. Worker lifecycle

### 6.1 Registration and kinds

S2-B registers a `PREPARE` handler in `src/worker/main.ts` beside
`SCRAPE`/`TAILOR`; `src/domain/enums.ts` `WorkKind` gains `PREPARE`
(the planned amendment in §13.3; `src/domain/step2.ts` carries
`Step2WorkKind = z.literal("PREPARE")` until then). Claim filtering
by registered kinds already isolates the new kind; no dispatcher
rewrite. `recoverStaleLeases` is kind-agnostic and requeues/expires
PREPARE items unchanged; the dispatch §9 TAILOR terminalization
branch is untouched, and S2-B adds a parallel PREPARE branch calling
a new `terminalizeExhaustedPreparation` that writes only the
preparation row (`FAILED` + versioned `LEASE_LOST` failure) — never
`jobs.tailoring_state`, never board status.

### 6.2 PREPARE handler stages and fencing

| Seq | Stage | Emitted | Source |
|---|---|---|---|
| 1 | `LOADING_INPUTS` | after the bound extraction payload, profile payload, and approved facts load and hashes verify | `provider` |
| 2 | `WAITING_FOR_PROVIDER` | immediately before the provider call (or cache load) | `provider`/`cached` |
| 3 | `VALIDATING_PROPOSAL` | before deterministic proposal validation | same |
| 4 | `STORING_PLAN` | before the plan-row insert transaction | same |
| 5 | `PUBLISHING_PLAN` | after the accepted-pointer flip commits | same |

Every preparation write rechecks the live-lease tuple in the same
short transaction (same shape as contracts §6, with the preparation
work item):

~~~sql
SELECT 1 FROM work_items w JOIN work_attempts a ON a.id=w.current_attempt_id
WHERE w.id=:workItemId AND w.kind='PREPARE' AND w.state='RUNNING'
  AND w.current_attempt_id=:attemptId AND w.lease_token=:leaseToken
  AND a.result='RUNNING' AND a.work_item_id=w.id
  AND julianday(w.lease_expires_at)>julianday(:serverNow);
~~~

`serverNow` is the trusted injected clock. Renewal reuses the F
formula `min(30000, floor(leaseDurationMs/3))`, one timer per
orchestration, cleared in `finally`; failed renewal aborts
write-free. Expired leases never revive before recovery.

Verification order in the handler (before any provider call):
payload schema → preparation row ownership (`jobId`,
`preparationId`) → `bindingHash` recompute → extraction still the
job's active extraction → profile payload hash + evidence hash
recompute → provider presence. Any mismatch is `INPUT_STALE` (new
explicit command required) except missing provider
(`CONFIGURATION`) and unapproved/foreign evidence
(`PROFILE_UNAVAILABLE`). No render, no `generation_requests` row, no
`job_analyses` row — preparation has its own storage (S2B2).

### 6.3 Crash recovery and caching

- Crash after the plan row commits: the successor attempt finds the
  committed plan for its work item, skips the provider call, emits
  all five stages with `source: "cached"` (stage 2 labeled "Loading
  the saved plan…"), and completes. The accepted-pointer flip is an
  idempotent conditional `UPDATE ... WHERE accepted_plan_id IS NULL
  OR accepted_plan_id <> :planId` guarded by the forward-only
  trigger; double-flip is a no-op.
- Crash before the plan row commits: bounded automatic retry
  (`maxAttempts = 3`, existing backoff) with no exactly-once claim
  for the remote call — a response lost after success may execute
  twice remotely but persists once (unique `(preparation_id,
  plan_hash)` plus attempt-scoped insert).
- Exhaustion without a plan: `terminalizeExhaustedPreparation`
  records `FAILED` + versioned `LEASE_LOST`; the clip and its READY
  job survive (S2B3).
- Successive cycles (supersession) reuse attempts numbering on the
  same work item; history stays append-only.

### 6.4 Limits

`maxAttempts = 3`; existing backoff; provider timeout 120 000 ms and
max output 65 536 bytes passed explicitly to the shared command
adapter (plans are smaller than tailor envelopes); preparation
payload ≤ 8 KiB; plan JSON ≤ 64 KiB (§3 caps). Provider concurrency
is the existing worker's single-claim loop — no new parallelism.

## 7. Claim-validation policy `step2-claims/1`

Normative algorithm, implemented pure across
`src/domain/step2Claims.ts` (string rules, support recomputation)
and `src/tailoring/step2policy.ts` (digests, quote verification,
verdict computation). Two entry points share the text rules:

- `verifyPlanQuotes(plan, canonicalJdText)`: every priority quote
  must satisfy `endByte > startByte` and
  `jdBytes.subarray(startByte, endByte).toString('utf8') === text`
  (UTF-8 byte ranges, never UTF-16 indices — same rule as §3.1, with
  fixtures placing non-ASCII text before a span). Failures reject the
  priority (proposal-level: the priority is dropped with reason, the
  plan still accepts when §7.2 passes).
- `validateStep2Segments(input)`: per-segment verdicts for exact
  edited text (draft validation and S2-D generation gating).

### 7.1 Segment validation

Input: `segments[]` (`segmentId`, `kind`, `roleId`, `text`,
`citedFactIds[]`); context: `planId`/`planHash`, bound snapshot
facts (`factId`, `statement`, `verification`, `profileVersionId`,
`employmentId`), accepted plan texts (`suggestionId → text`,
`angleId → summaryText`, master summary), master bullets
(`factId → text` from `step2-master-bullets/1`), bound ids, recorded
timestamps (`versionCreatedAt`, `planAcceptedAt`, `now`).

Definitions: `claimKey(t) = canonicalText(t)` (NFC, LF, NUL-strip,
trim — no case folding, no whitespace collapsing, no stemming).
`novelNumbers(t, citedTexts)`: digit-sequences (`\d[\d,./%]*`) in
`t` absent as substrings from every cited text.
`namedCompanies(t, employments)`: payload company names appearing in
`t` (case-folded substring).

Verdict rules, evaluated in order; the first match wins:

1. `CHRONOLOGY`: `versionCreatedAt > planAcceptedAt`, or any cited
   fact's `profileVersionId ≠ boundProfileVersionId`, or
   `planAcceptedAt > now` → `needs-evidence`. (Defensive: unreachable
   through honest services, which bind before planning before
   validating.)
2. `UNKNOWN_FACT` / `FACT_NOT_APPROVED` / `FOREIGN_FACT`: a cited id
   missing from the snapshot, not `APPROVED`, or owned by another
   version → `needs-evidence`. Reference existence alone never
   passes: every later rule additionally requires text equality.
3. `FOREIGN_ROLE_FACT`: a cited fact with non-null `employmentId ≠`
   the segment's role employment → `needs-evidence`. Transferable
   facts (`employmentId` null) may support any role by exact text
   only; role-owned facts never cross employers. This is the
   cross-employer contamination guard.
4. `EXACT` pass: `claimKey(text)` equals `claimKey` of a cited
   approved fact statement (`match: exact-fact`), of an accepted
   plan text of the bound plan (`match: exact-plan`), or of the
   bound master bullet for the edited bullet (`match: exact-master`)
   → `supported` with the responsible `factIds`. Equality precedes
   the novelty diagnostics because approved content carries its
   entities: a verbatim master summary containing "6 years" is
   supported even though no single cited fact states it.
   `DERIVATION` pass (same step): the text satisfies an allowlisted
   deterministic derivation manifest carried on the segment (the
   active tree's allowlist is exactly: summary
   `final_text`/`fact_ids` manifest equality per `validator.ts`,
   plus `canonicalText` normalization itself). S2 adds no new
   derivations; paraphrase, re-casing, and token-overlap similarity
   are not derivations.
5. `NEW_METRIC`: `novelNumbers` non-empty → `needs-evidence`
   (fabricated metrics). `NEW_EMPLOYER`: a named company that is
   neither the segment role's employer nor an employer of a cited
   transferable fact → `needs-evidence` (fabricated responsibility
   attribution). These entity checks are necessary-condition
   failures only: their absence never implies support.
6. Default `REWORDED`: no equality, no manifest → `needs-evidence`.
   Equivalent supported wording lands here until it travels the
   explicit evidence-governance path (§7.3).

The pure function takes no LLM verdict input: provider `match_status`
values are steering for ranking, never evidence. Token overlap is
never sufficient for `supported` (S2D1 forbids it explicitly); the
only similarity the policy trusts is exact normalized equality plus
manifest derivations.

`reason` strings are stable machine codes (`REWORDED`,
`NEW_METRIC`, `FOREIGN_ROLE_FACT`, …) ≤ 200 chars; human copy lives
in S2-C renderers, never in verdict rows.

### 7.2 Proposal validation (worker, plan accept)

Per-item checks before a plan row is accepted:

- Priorities: quote verification (§7 head) + `importance` preserved
  from the proposal + `support` recomputed by the pure
  `recomputePrioritySupport`: drop cited ids that are unknown,
  unapproved, or foreign-owned (with reason); of the kept ids,
  `supported` when ≥1 is employment-linked, `related` when ≥1 kept
  and all are transferable (`employmentId` null), else `gap`. A
  priority whose quote fails verification is dropped with reason;
  required NetSuite with no support stays a visible `gap` — never
  padded, never promoted.
- Angles: `factIds` exist/approved/owned; the two angles must be
  textually distinct (`claimKey` inequality) and distinct from
  keep-master; duplicates collapse to one (no padded second angle).
- Suggestions: `roleId` names a payload employment; `factIds`
  exist/approved/owned by that role (or transferable); no novel
  numbers versus cited statements+metrics; no company name outside
  the role employer (employer-swap → unusable); quote-free. Failures
  mark the suggestion `usable: false` with `unusableReason` — the
  plan still accepts. A plan with zero usable suggestions accepts
  (sparse case): the editor shows master bullets only.
- Whole-proposal rejection (no plan row, `INVALID_RESPONSE`) only
  for: schema failure, binding mismatch, zero priorities with a
  non-empty JD (provider returned nothing usable — retryable), or
  every priority failing quote verification.

`validation_json` records per-item outcomes with the same stable
reason codes. Provider/model/prompt/proposal lineage columns (§3.2)
bind reproducibility to exact bytes, never to model identity.

### 7.3 Approved-wording chronology (resolved)

Architecture §7 requires an approved wording variant to predate and
belong to the exact candidate profile version used to create the
resume. The active tree stores no per-fact approval timestamp
(`candidate_facts` carries `createdAt` only; `verification` flips
`PENDING → APPROVED/REJECTED` one way), so S2 proves chronology over
recorded version/plan lineage instead of inventing timestamps:

- Supporting text must belong to the captured
  `profileVersionId` (rule 1–3 above) — the version active at intake
  acceptance, hence necessarily created before the plan.
- The plan's `created_at` (`planAcceptedAt`) must precede generation
  submission; S2-D rechecks `planHash` + `draftHash` + policy
  versions at G time.
- A newly approved fact/wording lands in a NEWER profile version,
  which by rule 1 cannot support the captured plan's drafts. The
  remedy is explicit re-preparation binding the newer version
  (§8.6), never silent rebinding.

No hidden master mutation exists in any path: editor drafts, plans,
and validations reference master bytes; only the existing
profile-version creation path writes new master content.

### 7.4 Race handling and persisted verdicts

- Any edit changes `draftHash`; old verdict rows no longer match and
  are ignored (never applied to newer text). Late-arriving verdicts
  for a superseded `draftHash` are stored but inapplicable.
- S2-D generation replays validation over the exact frozen bytes and
  requires a matching `step2_draft_validations` row; included
  `needs-evidence` segments block with 422 `UNRESOLVED_EVIDENCE`
  (ΔQ1 = 0). Excluded bullets are not segments and never block.
- Stale asynchronous verdicts cannot enable Generate: the G path
  recomputes `draftHash` from frozen inputs and compares, never
  trusts a client-supplied validation id alone.

### 7.5 Validate-endpoint segment derivation (S2-B, 2026-09-17)

`ValidateDraftBodyV1` carries no per-segment citations, so the
validate service derives them deterministically from the bound
plan (advisory verdicts; S2-D's generation gate recomputes over
the full frozen draft):

- One summary segment (`roleId` null) citing the union of all
  usable-suggestion and angle `factIds` of the bound plan.
- `add`/`replace`-with-suggestion: one segment citing that
  suggestion's plan `factIds`; `editedText` (when present) replaces
  the suggestion text as the segment text.
- `replace`-with-text: one segment citing `[targetFactId]`.
- `edit` on a suggestion target: one segment citing that
  suggestion's plan `factIds`, `roleId` from the matching `add` op
  (same `suggestionId`, first in order; null when none matches).
- `edit` on a bullet target: one segment citing `[target.factId]`
  with the bullet's role.
- `exclude`: no segment (excluded content never blocks).

Derivation only affects diagnostics and citation validity; the
equality gate still decides support, so verdicts stay
conservative-correct.

### 7.6 Limitations (recorded, not waived)

`step2-claims/1` is deliberately conservative: legitimate
paraphrases, synonym swaps, re-casing, and punctuation-only edits
all yield `needs-evidence` until grounded through evidence
governance. It cannot detect false claims phrased with fact-identical
entities but novel assertions that reuse only old numbers ("led" vs
"joined" with identical digits passes the entity filter but fails
equality → still `needs-evidence`; equality is the actual gate).
Technology/responsibility novelty without new numbers or payload
company names reports the generic `REWORDED` reason; the verdict
(`needs-evidence`) is still correct, only the diagnostic is coarse.
Embeddings/KeyBERT/Transformers.js are explicitly out of this
increment; any future semantic policy ships as `step2-claims/2`
with its own fixtures and never reinterprets `/1` verdicts.

## 8. Intake binding boundary (S2A4)

### 8.1 Capture point

At intake acceptance — `submitIntakeBatch`'s per-line persist for
pastes and the clip ingest's item persist for the 1-click clipper
(both paths already create `intake_batches`/`intake_items` rows) —
S2-B inserts the `step2_preparations` row in the same short
transaction that enqueues the SCRAPE item:

- Read the global default profile (`is_default`, the one global
  choice) and its ACTIVE version; compute `profilePayloadHash`
  (`SHA256(canonicalJson(parseStoredProfilePayload(payloadJson)))`)
  and `evidenceHash` (§2); resolve `masterSourceId` when present.
- Missing default profile or missing active version or zero approved
  facts: insert NO row; the scrape proceeds normally. The batch/item
  reads `preparation: null` until explicit recovery (§8.4). Never
  adopt a later default silently.
- In-batch duplicates and cross-batch duplicates (tracked or queued)
  insert no row; they reuse the owning job's lineage (§8.3).

Capture precedes asynchronous scraping; the row's `job_id` stays NULL
until the SCRAPE worker creates the shell.

### 8.2 Extraction linkage and auto-schedule

In `persistFetchOutcome`'s success branch (same transaction that
rests the job in READY), when a preparation row exists for the
intake item and no live PREPARE work exists for the job: link
`job_id` + `extraction_id`, insert the PREPARE work item
(`prepare:{jobId}:{preparationId}:{extractionId}`, `PreparePayloadV1`), set state
`QUEUED`. Skip (leaving the row `PENDING`) when: extraction failed,
provider key absent (`awaiting-provider`, recoverable via explicit
command after configuration), or a live TAILOR run exists (never
compete with explicit generation; the explicit command schedules
later). Linkage never writes `generation_requests`, versions,
reviews, or applications. This is the planned R-ADR-015 amendment:
extraction may enqueue preparation only (§13.1).

### 8.3 Deduplication

- Same-URL re-clip/re-paste resolves to the existing job; the new
  intake item gets no preparation row. Batch reads show the owning
  job's preparation state on the duplicate item (lineage reuse, no
  retargeting).
- Retried intake (same batch resubmission) reuses the existing row
  by `intake_item_id`; retries never rebind or duplicate.
- Preparation is per job: the second ENQUEUED item for a job is
  impossible through honest intake (canonical dedupe + idempotency
  race rule); a defensive `UNIQUE(job_id)` violation fails closed
  as a duplicate, reusing the existing row.

### 8.4 Missing-profile recovery (explicit)

`POST .../tailoring/preparation` with `profileId` on a bound or
unbound job: resolve that profile's ACTIVE version now, show the
chosen `profileId`/`profileVersionId` in the reply, and (when no row
exists) create the row bound to it, then schedule per §4.1. The
command is explicit, user-visible, and recorded (`last_operation_*`);
it never adopts "current default" implicitly — the body names the
profile. Unknown profile → 404; profile with no active version or no
approved facts → 422 `PROFILE_NOT_READY`.

### 8.5 Legacy jobs (explicit preparation, no backfill)

Jobs accepted before 0009 have no row (`ABSENT`). The same explicit
command with `profileId` creates and schedules; without `profileId`
it fails 422 `PROFILE_NOT_READY` (nothing captured to reuse).
Upgrade and migration perform zero AI calls and zero queue inserts.
No automatic mass backfill exists.

### 8.6 JD supersession and profile edits after enqueue

- Later Settings edits (new versions, new facts, changed default)
  never invalidate a captured plan: all preparation/plan/editor/
  validation/generation checks compare against the CAPTURED binding
  (`profileVersionId`, `evidenceHash`, `masterProjectionHash`), not
  the active pointers. This amends the D/E active-version freshness
  rule for Step 2 paths only; JD freshness is never waived (§8.7).
- A newer active extraction (re-scrape) makes the accepted plan
  `PLAN_STALE` for plan/draft-validate/generate reads. Recovery is
  the explicit POST preparation (no `profileId` needed): P relinks
  `extraction_id`, keeps the profile binding and the old accepted
  plan, and schedules a new cycle; the new plan's
  `supersedes_plan_id` names the old. Until the new plan publishes,
  generation stays blocked; the old plan remains inspectable.
- Evidence revocation: the active tree has no APPROVED→REJECTED
  transition (`verifyFact` moves `PENDING` only) and facts are
  otherwise immutable, so the only revocation signals are
  re-read failures — missing fact row, `verification ≠ APPROVED`,
  statement drift versus `evidenceHash`, or ownership drift. Every
  preparation schedule, plan accept, draft validation, and
  generation recomputes the evidence digest and compares; any drift
  fails closed (`PROFILE_UNAVAILABLE` in worker paths, 422
  `PROFILE_NOT_READY` in web paths). If a future order adds explicit
  revocation, these hooks already enforce it.

### 8.7 JD freshness (never waived)

Plan accept, draft validate, workspace v2 save with a plan binding,
and S2-D generation all require `plan.extractionId =
jobs.active_extraction_id` and `jdHash` recomputation over the live
extraction bytes. Changed JD always forces the §8.6 cycle; no
exception parallels the profile-capture rule.

## 9. Provider planning schema, prompt, and rewrite policy

Preparation reuses the existing provider stack only: `scripts/ai-
provider.mjs` dispatch (openrouter/google/meta), `scripts/tailor-
provider.mjs` spawning, `TailoringProvider` adapter boundary, and
the command adapter's exit-code taxonomy (10/11/12/13/14). No
KeyBERT, Transformers.js, Python, or new dependency. S2-B extends
`src/tailoring/contract.ts` with the two schemas below (published
here; the pure `src/domain/step2.ts` carries identical Zod text so
contract tests pin them before S2-B):

~~~ts
export const PreparationInputV1 = z.object({
  schemaVersion: z.literal("preparation-input/v1"),
  promptVersion: z.literal("prepare-prompt/v1"),
  jobId: z.string().min(1),
  jobTitle: z.string(), company: z.string(),
  jdSnapshotId: z.string().min(1), jdText: z.string().min(1).max(200_000),
  candidateSnapshotId: z.string().min(1),
  profile: StoredProfilePayload,
  approvedFactIds: z.array(z.string().min(1)).max(500),
  masterBullets: z.array(z.object({ roleId: Key, factId: Key, text: z.string().min(1).max(2000)
    }).strict()).max(500),
  budgets: z.object({ priorities: z.int(), suggestions: z.int(), angles: z.int() }).strict(),
}).strict();

export const PreparationProposalV1 = z.object({
  schemaVersion: z.literal("preparation-proposal/v1"),
  jdSnapshotId: z.string().min(1), candidateSnapshotId: z.string().min(1),
  priorities: z.array(z.object({
    quote: PlanQuote, count: z.int().positive(), category: z.string().max(80),
    importance: z.enum(["required", "preferred", "unspecified"]),
    matchStatus: z.enum(["matched", "partial", "gap", "unsupported"]),
    factIds: z.array(z.string().min(1)).max(100),
  }).strict()).max(20),
  angles: z.array(z.object({ title: z.string().min(1).max(80),
    summaryText: z.string().min(1).max(4000),
    factIds: z.array(z.string().min(1)).min(1).max(100) }).strict()).max(2),
  suggestions: z.array(z.object({ roleId: z.string().min(1).max(128),
    text: z.string().min(1).max(2000),
    factIds: z.array(z.string().min(1)).min(1).max(20) }).strict()).max(10),
  rationale: z.string().max(2000),
}).strict();
~~~

`profile` is the domain `StoredProfilePayload` (stored v1/v2
union), not the tailor envelope's legacy `CandidateProfileInput`:
preparation hashes it against the captured version. `jdText` is
capped at 200 000 chars (preparation input, not the 500 000 tailor
cap); larger JDs fail closed as `INPUT_STALE` with guidance to
shorten, never truncated silently. Snapshots are the
existing immutable `candidate_snapshots`/`jd_snapshots` rows created
at schedule time (P creates them; reuse by hash when identical bytes
recur).

Prompt `prepare-prompt/v1` (normative content; S2-B stores the exact
string as a checked-in constant and records its hash in
`step2_plans.input_hash` lineage):

1. Role: quote JD requirements exactly; propose resume angles and
   bullets grounded ONLY in the supplied approved facts.
2. Every priority quote must be a verbatim JD substring; supply
   byte offsets counted in UTF-8 from the JD start.
3. Rank by importance to the role (required first), independent of
   candidate support; mark support honestly (`matched`/`partial`/
   `gap`/`unsupported`) — the grade is advisory, deterministic code
   recomputes it.
4. Angles and suggestions must cite the fact ids they rest on; never
   invent metrics, technologies, employers, dates, or
   responsibilities; never move experience across employers.
5. Prefer reusing fact/master wording verbatim; flag any necessary
   rewording by keeping cited ids exact (deterministic validation
   decides support, not this proposal).
6. Fewer than three priorities or zero suggestions is acceptable
   when evidence is sparse; never pad with boilerplate.
7. Output strict JSON matching `preparation-proposal/v1` only; no
   scores, paths, or approval assertions.

Grounded rewrite policy: provider wording is a proposal. A
suggestion becomes a usable plan item only through §7.2 checks; it
becomes a resume claim only through §7.1 `supported` verdicts on
exact edited text at generation time. The provider cannot choose
plan acceptance, hashes, pointers, or coverage.
