# v1.3 E — Step 2, G dispatch, v2 provider/compiler handoff for F, G, H

WO-1.3-E interface publication (2026-09-16). Step 2 focus
controls write durable drafts with serialized autosave and
visible CAS recovery; transaction G dispatches v3 queue payloads
with exact input snapshots, operation replay, and readiness
mapping; the provider v2 envelope and the deterministic focus
compiler adapter are implemented and tested. No web route makes
a model call. This document is the exact contract surface:
signatures, error names, UI protocol, and test evidence.
Normative behavior stays in
`docs/tailoring-contracts-v1.3.md`.

## 2. Transaction G (`src/server/generations.ts`)

### 2.1 `submitGeneration(handle, input, deps)`

Input: `{ jobId, requestId, workspaceRevision,
observedRowVersion, now? }`. `requestId` is the caller's
operation UUID (minted once per Generate click by Step 2);
`workspaceRevision` is the exact stored focus revision to run;
`observedRowVersion` is the job CAS token.

One outer SQLite transaction performs readiness →
idempotency → snapshot → request → queue → workspace-submit
marking (`markWorkspaceSubmitted`), or rolls everything back.
Behavior:

- Exact stored focus: the run binds `Q2.focus_json` at the
  observed revision plus its recommendation snapshot. The
  legacy default-profile fallback is gone from this path;
  `requestGeneration`/`requestRevision` in
  `src/server/tailoring.ts` now take exact immutable focus and
  the caller operation ID.
- Replay: identical `(requestId, canonical bytes)` returns the
  original reply with `replayed: true` and writes nothing —
  including when the first run FAILED (no requeue). Same-ID
  changed bytes → `409 IDEMPOTENCY_MISMATCH` with zero
  writes. A fresh ID while a run is live → `409
  GENERATION_BUSY` with zero writes.
- Readiness (precedence profile → JD → provider): unreadiness
  → `422 PROFILE_NOT_READY` / `422 PROVIDER_NOT_READY` /
  evidence/JD equivalents; stale/cross revisions →
  `409 WORKSPACE_CONFLICT` / `409 JOB_CONFLICT`; rejected jobs
  → `409`; corrupt storage → `503`. All rejections leave Q1,
  Q2, Q4, and snapshot counts unchanged (asserted by count).
- v3 queue payload: `TAILOR_QUEUE_SCHEMA_VERSION_V3` with the
  input extension (focus + recommendation hashes) inside the
  canonical hash; existing keyword/directive columns store the
  verified selected-text/guidance projections.

### 2.2 `POST /api/jobs/:id/tailoring/generations`

Body `tailoring-submit/v1` (`requestId`, `workspaceRevision`,
`observedRowVersion`). Replies: `202` created, `200` replayed
(`replayed: true`), `409` conflict/busy/mismatch,
`422` unreadiness, `503` corrupt storage — all as ErrorBody
with `code`, `field` where applicable, and
`currentWorkspaceRevision` / `currentRowVersion` advisories.
CSRF/Host/Origin via the shared tailoring gate; no provider
execution in the route.

### 2.3 Legacy request writers

`requestGeneration`/`requestRevision` keep the legacy
guidance-only path for already-queued v2 work until H cuts
over; v1.3 submits with `workspaceRevision` route through
transaction G. Duplicate discipline changed: same-ID changed
bytes is a 409 (never a silent dedupe), and live-run fresh
IDs are `GENERATION_BUSY` (never an attach). The legacy
tailoring/retry/A5 suites were updated to this discipline.

### 2.4 Seams for F (execution)

- Stored per request: immutable request inputs (focus +
  recommendation snapshots, selected keywords, directives,
  revision note up to v2's 4000 chars), the v3 queue payload,
  and canonical hashes that reconstruct Q3.
- F verifies the v3 payload with the existing v2 reader
  unchanged, then calls `orchestrateTailoring` with
  `focus` + `recommendations` (exact stored snapshots) plus
  the request's `selectedKeywords` / `directives` /
  `revisionNote`. That selects the v2 envelope (§3) and
  returns `focusOutcomes` alongside the draft.
- Persistence decision left to F/G: unsupported summary
  sentences already persist as `summary-{index}` analysis
  gaps through `recordAnalysis`; per-field mapping /
  selected-phrase / theme outcomes are returned on
  `OrchestrationSuccess.focusOutcomes` and await F/G's
  persistence + G's inspector display.

## 3. Provider v2 envelope and compiler steering (§3.2)

### 3.1 Envelope (`src/tailoring/contract.ts`)

- `TailoringInputV2`: every v1 steering field plus exact
  frozen `focus` / `recommendations`; `revisionNote` bound is
  explicitly 4000 chars (never truncated to v1's 2000).
- `TailoringInputAnyVersion`: discriminated-union reader for
  the migration window; `TailorPromptVersion` accepts
  `tailor-prompt/v1` and `tailor-prompt/v2`.
- Attempt/audit readers accept both prompt versions;
  historical v1 records keep their v1 label. Provider output
  stays `ResumeProposalV1`.

### 3.2 Transport (`src/tailoring/commandAdapter.ts`, `scripts/tailor-provider.mjs`)

- The adapter validates the envelope against the union
  before spawning: unsupported schema versions fail with
  `unsupported tailoring input version` without spawning;
  supported-but-invalid envelopes fail with paths/codes
  only. It transports complete canonical bytes and records
  the envelope's own prompt version in the attempt, so
  `inputHash` covers the frozen v2 bytes.
- The sidecar gates versions/prompts/snapshots/steering
  bounds (`validateTailoringInput`, exported for tests)
  before any remote call or fallback, and appends a frozen
  `FOCUS STEERING` section (`buildFocusSection`) naming the
  chosen theme, requested summary direction, and
  phrase→role mappings as evidenced-only steering. The
  Google/Meta/OpenRouter client scripts needed no change:
  they transport the adapter-built prompt and never parse
  the envelope.

### 3.3 Compiler adapter (`src/tailoring/focusSteering.ts`)

Pure over frozen inputs (`FOCUS_STEERING_POLICY_VERSION =
"focus-steering/v1"`):

- `orderRankedFactsWithFocus`: reorders the ranker's
  eligible output only — mapped eligible facts, then
  selected-term eligible facts, then existing stable rank
  (ties: legacy index, then fact ID). Same fact set, same
  budgets, no claim/template path. Invalid mappings (unknown
  role/phrase, foreign or unapproved facts) steer nothing.
- `evaluateFocusOutcomes`: per-field verdicts in the
  existing coaching vocabulary (`used`, `omitted-by-budget`,
  `unsupported`, `not-assessed`), tied to mapping index /
  phrase ID, requirement IDs, and supporting fact IDs.
- Summary direction never edits generated text:
  whole-direction matches to approved wording report
  `used`/`omitted-by-budget`; unbacked KPI tokens or
  technical terms and otherwise unapproved sentences become
  `summary-{index}` gaps via `summaryGapDrafts`; supported
  paraphrases the compiler cannot assess report
  `not-assessed`.
- `buildTailoredDraft` accepts optional `focusSteering` and
  applies the reorder before section selection; the v1 path
  is byte-identical.

### 3.4 Orchestration (`src/tailoring/orchestrate.ts`)

Optional `focus` + `recommendations` inputs select the v2
envelope (a lone snapshot fails closed with `STALE_INPUT`
before any provider call); unsupported summary sentences
join the accepted gaps; the audit records the attempt's
prompt version; success carries `focusOutcomes` (empty on
v1 runs).

## 4. Step 2 UI (`components/tailoring/Step2Focus.tsx`, `./focusDraft.ts`)

Rendered by `TailoringWorkflowShell` at Step 2. No mockup
imports; no provider calls; missing extraction renders a
guidance-only surface with zero fetches.

### 4.1 Control map (§5)

- Candidate profile: select resolves the exact active
  version → GET recommendations → W with the changed
  binding. Switching preserves free guidance, clears
  incompatible selections/mappings, resets theme/summary,
  and announces what dropped. The global default is never
  touched.
- Preview master: dialog rendering the existing
  version-specific preview payload (read-only).
- Edit candidate profile: `/master-resume` with
  `?profile=&version=` when a binding exists, bare
  otherwise; returning with a changed master shows the
  stale-binding prompt (also on window-focus revalidation
  and recommendation 409s). Never a silent repin.
- Cloud/category/search/inspector/evidence: local filtering
  over `RecommendationV1` with real counts, excerpts,
  offsets, and fact references; zero mutations.
- Keyword select/deselect/Clear: W on `selectedPhraseIds`;
  gap/uncertain/over-128-char phrases show reasons and stay
  disabled. Clear affects selected terms only.
- Preset/themes/summary: preset applies the served bytes
  verbatim; theme use copies the server direction; summary
  Edit stages a local buffer (Cancel: zero writes), Save
  and Reset persist via W (Reset reads the frozen master
  summary first).
- Phrase→role mapping: drag/drop plus keyboard Assign
  selects and per-mapping remove. Evidence defaults to
  phrase∩role overlap, else the role's first owned fact;
  roles without facts stay disabled. Mappings steer
  ranking only — job phrases never enter resume content.
- Starters/guidance: starter append + textarea with
  500ms-debounce autosave; over-1000-char text shows a
  field error and never PUTs (no silent truncation).
- Back: flushes pending edits first; on conflict/error it
  stays with the failure surfaced instead of losing input.

### 4.2 Save protocol

Discrete actions flush immediately; typing debounces at
500ms. All saves serialize through one promise chain: a
single in-flight PUT, the latest edit queued against the
returned revision. Status is always honest (`Saved ·
revision N` / `Saving…` / `Unsaved changes` / conflict /
error — never `Saved` while pending). A 412 stops
autosave, retains local input, and offers explicit Reload
saved draft / Reapply my edits onto latest (both re-read
the server first). Page unload warns while anything is
unconfirmed. No browser storage is authoritative.

### 4.3 Generation submission

Generate flushes the draft, mints one operation UUID, and
POSTs the exact `tailoring-submit/v1` bytes. `202`/`200`
show the queued/replayed state with the request ID and a
Step 3 reload; certain 4xx/5xx failures surface code +
message (workspace/job conflicts also update local CAS
state); network or unreadable responses keep the exact
bytes in a session replay cache (`tailor-pending-generation:{jobId}`,
shape-validated) with Replay-same-submission / Discard.
Reloading resurfaces an uncertain submission; replay is
byte-identical and can never fork a second run.

### 4.4 For G (review UI)

The Request-changes/New-version modal and all Step 4
behavior are G's, including the E8 modal interaction leg.
E's service legs guarantee the modal's submission path:
draft saves stay workspace-scoped and G REVISION is
all-or-nothing (review + request + queue + CAS).
