# WO-1.3-S2-CP-A — Step 2 correction frozen contracts

Status: normative for WO-1.3-S2-CP-B/C. This document publishes exact
versioned schemas, DDL, endpoints, state machines, the
`step2-claims/2` provenance policy, and the one Generate transition.
Nothing here is implemented: no migration is applied, no route or
handler is changed, no provider is invoked, no UI is cut over.
S2-CP-B/S2-CP-C implement against these bytes; any deviation amends
this document first.

Authority: [Step 2 correction scope](../step2-correction-scope-v1.3.md)
(controlling product/engineering scope),
[S2-A contracts](v1.3-step2-contracts.md) (historical v1 formats —
never reinterpreted), [acceptance](../acceptance-v1.3.md)
S2CPA1–S2CPA5, architecture §7 (tailoring/artifact contract),
R-ADR-026 (user-authored text with explicit provenance),
R-ADR-015/017/022/023 (explicit generation, immutable inputs,
fenced progress).

Controlling product decision: the user is authoritative for text
they deliberately edit. A user edit is allowed into the generated
resume, preserved verbatim, labeled **User edit**, and never blocked
merely because the system cannot prove it from candidate evidence.
AI proposals and user edits are never presented as verified facts.

### 1.4 Editor draft v2

Operation shapes match v1. `summarySource` becomes
`summaryOrigin` (no `"edited"` value): the origin is always named
so anchor retention survives edits, and edited-ness is derived
server-side by exact-text comparison — the client cannot declare
it.

~~~ts
export const Step2DraftOperationV2 = z.discriminatedUnion("op", [
  z.object({ op: z.literal("add"), operationId: Id,
    suggestionId: z.string().regex(/^sug-[0-9]{3}$/),
    roleId: Key, editedText: z.string().max(2000).nullable() }).strict(),
  z.object({ op: z.literal("replace"), operationId: Id, targetFactId: Key,
    roleId: Key, suggestionId: z.string().regex(/^sug-[0-9]{3}$/).nullable(),
    editedText: z.string().min(1).max(2000).nullable() }).strict(),
  // refinement: replace carries exactly one of suggestionId/editedText
  z.object({ op: z.literal("exclude"), operationId: Id,
    targetFactId: Key }).strict(),
  z.object({ op: z.literal("edit"), operationId: Id,
    target: z.discriminatedUnion("kind", [
      z.object({ kind: z.literal("suggestion"),
        suggestionId: z.string().regex(/^sug-[0-9]{3}$/) }).strict(),
      z.object({ kind: z.literal("bullet"), factId: Key }).strict(),
    ]),
    text: z.string().min(1).max(2000) }).strict(),
]);

export const Step2SummaryOrigin = z.enum(["master", "angle-1", "angle-2"]);

export const Step2DraftV2 = z.object({
  schemaVersion: z.literal(STEP2_CORRECTION_VERSIONS.draft),
  planId: Id,
  planHash: Hash,
  summaryText: z.string().max(4000),
  summaryOrigin: Step2SummaryOrigin,
  operations: z.array(Step2DraftOperationV2).max(50),
}).strict();
// refinement: operation ids unique within the draft
~~~

Semantic rules (enforced by W-v3, pinned by contract tests):
`operationId` unique; array order is display/apply order; `add`
with `editedText` equals add-then-edit atomically (identical text
is not an edit); `replace` carries exactly one of
`suggestionId`/`editedText`; `replace`-with-text always records
user authorship; repeated Use/drop of the same usable suggestion
in the same role collapses to the existing `operationId`;
`exclude` of an already-excluded bullet is a no-op; undo removes
the operation (source facts never mutate); `edit` on a suggestion
target applies to the added/replaced instance; `edit` on a bullet
target rewords a master bullet in place (still attributed to its
role). A `replace` naming a `suggestionId` requires that
suggestion `usable` in the bound plan; unusable suggestions and
gap priorities can never enter an `add`/`replace`. Every op
`roleId` must belong to the server-derived eligible set (§7.3):
master-bullet ops stay in their own role, suggestion ops land in
an eligible role — otherwise 422 `INVALID_SELECTION`.

## 2. Identities, hashes, and digests

All digests are lowercase hex SHA-256 over UTF-8 bytes, computed
with `canonicalJson` (key-sorted, no whitespace) or the stated raw
bytes. Implement in
`src/tailoring/step2CorrectionPolicy.ts` (hashes live in tailoring
per the domain purity guard; schemas stay in
`src/domain/step2Correction.ts`). Historical v1 digests
(`evidenceHash`, `bindingHash`, `priorityId`, `masterProjectionHash`,
`planHashFor`, `draftHashFor`, `prepareOperationHashFor`,
`hashStep2WorkflowInput`) are unchanged and recompute
byte-identically — §12 pins them.

| Digest | Definition |
|---|---|
| `correctionPlanHash` | `SHA256(canonicalJson(PreparationPlanV2))` |
| `correctionDraftHash` | `SHA256(canonicalJson({planId, planHash, summaryText, summaryOrigin, operations}))` |
| `correctionSegmentTextHash` | `SHA256` of exact submitted segment bytes |
| `correctionSegmentNormalizedHash` | `SHA256(canonicalText(segment bytes))` |
| `correctionManifestHash` | `SHA256(canonicalJson(provenanceManifest))` (entries in segment order) |
| `step2-request-input/v2` | `SHA256(canonicalJson({schemaVersion, workspaceRevision, planId, planHash, draftHash, validationId, provenanceManifestHash, candidateSnapshotId, masterText, masterTextHash, projectionVersion, policies}))` with `policies = Step2PolicyVersionsV2` |
| `prepare` idempotency key | unchanged: `prepare:{jobId}:{preparationId}:{extractionId}` |
| `v13_one_live_prepare` | unchanged partial unique index (no DDL change) |

`priorityId` reuses the existing `phraseIdFor` verbatim (never
reimplemented). `evidenceHash`, `bindingHash`, and
`masterProjectionHash` keep their S2-A definitions: the correction
changes derivation and linkage, not the captured-evidence
digests. `masterBulletsByRole` (`step2-master-bullets/1`) is
unchanged.

`claimKey(t) = canonicalText(t)` (NFC, LF, NUL-strip, trim — no
case folding, no whitespace collapsing, no stemming) decides
"sameness" for provenance derivation. Provider-declared similarity
is never consulted.

## 3. SQL and Drizzle specification (migration 0011)

S2-CP-B implements `drizzle/0011_step2_correction_versions.sql`
from this section. Conventions mirror 0008/0009: `TEXT` ids,
`CHECK` ranges/enums, named triggers with
`RAISE(ABORT, '<NAME>')`, UTC `...Z` timestamps with `strftime`
guards, byte-length caps via `length(CAST(x AS BLOB))`, hash
checks via `NOT GLOB '*[^0-9a-f]*'` plus `length() = 64`.

No new tables and no new columns. The correction widens two
version `CHECK`s so v2 rows can coexist with v1 rows in the same
append-only histories; all new semantics live in versioned JSON
plus server derivation. SQLite cannot alter a `CHECK`, so 0011
rebuilds the two tables exactly as 0009 rebuilt `work_items` (new
table, copied rows, drop, rename; `CHECK` expressions name their
columns unqualified so they survive the rename).

### 3.1 Preflight and guards

- The migration aborts unless zero `RUNNING` work rows of any
  kind exist (extends the 0009 upgrade preflight in
  `src/db/migrate.ts` to cover 0011; a live lease cannot survive
  a rebuild window honestly).
- 0011 performs no backfill: v1 rows keep their exact bytes and
  hashes; no preparation/plan/validation/generation rows are
  inserted, updated, or deleted; upgrade performs zero provider
  calls and zero queue inserts.
- After each rebuild, the migration asserts the copied row count
  equals the pre-rebuild count (a `SELECT RAISE(ABORT,
  'CORRECTION_REBUILD_LOSS') WHERE (SELECT COUNT(*) ...) <>
  ...` guard), then runs `PRAGMA foreign_key_check` semantics via
  the existing migration-test FK assertion (Q8 empty).

### 3.2 `step2_plans` rebuild — widen `s2_plan_versions`

Recreate `step2_plans` with every column, index, and trigger
identical except:

~~~sql
CONSTRAINT s2_plan_versions CHECK(
  prompt_version IN ('prepare-prompt/v1', 'prepare-prompt/v2') AND
  proposal_schema_version IN ('preparation-proposal/v1', 'preparation-proposal/v2') AND
  claims_policy_version IN ('step2-claims/1', 'step2-claims/2')),
~~~

plus a cross-version lineage guard (new, named):

~~~sql
CONSTRAINT s2_plan_lineage CHECK(
  (prompt_version = 'prepare-prompt/v1') =
    (proposal_schema_version = 'preparation-proposal/v1') AND
  (prompt_version = 'prepare-prompt/v1') =
    (claims_policy_version = 'step2-claims/1')),
~~~

so v1 prompt/proposal/claims travel together and v2 travels
together — mixed lineage rows are rejected. Copy all columns in
declared order; drop the old table (this drops `s2_plans_hash`,
`s2_plans_preparation_id`, `s2_plan_no_update`,
`s2_plan_no_delete`, `s2_plan_owner`); rename; recreate every
index and trigger byte-identical. Triggers on OTHER tables that
name `step2_plans` (`s2_prep_accepted_forward`) must be dropped
before the rebuild and recreated byte-identical afterwards —
the rename cannot run while a trigger references the table
(same rule as 0009's `v13_progress_fence` handling).

`plan_seq` continues per preparation across versions: a v2 plan
superseding a v1 plan takes the next `plan_seq` with
`supersedes_plan_id` naming the v1 row. The forward-only
accepted-pointer trigger is version-agnostic and unchanged.

## 4. HTTP operations

All endpoints keep their S2-A paths, `application/json`,
`Cache-Control: no-store`, Host/Origin/mutation protections, and
the 128 KiB pre-parse body limit (excess → 413
`INVALID_REQUEST`). Failures use `ErrorBody`; no new error code
is introduced — v2 paths reuse the existing set
(`INVALID_SELECTION` for structural/ownership/link violations,
`BUDGET_EXCEEDED` for the 64 KiB frozen-input byte cap only,
`PLAN_STALE` for drift). Bullet/summary counts are advisory
length guidance (§1.5, §7.6), never a rejection.
`UNRESOLVED_EVIDENCE` is retained for the v1 generation path
only and is never emitted for v2 drafts: provenance never
blocks.

### 4.1 Transaction P/PR — unchanged mechanics, v2 lineage

P and PR run exactly as S2-A §4.1–§4.2 (idempotency-first,
job CAS, busy guard, readiness order, supersession relink,
`prepare:{jobId}:{preparationId}:{extractionId}` key, ΔQ1 = 0,
ΔQ4 = 0). The worker (§6) executes new cycles with
`prepare-prompt/v2` / `preparation-proposal/v2` and persists
v2 plans with `step2-claims/2` lineage. Retries of v1 cycles
replay v1 bytes; only NEW cycles (explicit P after
supersession or first preparation) produce v2 plans. A v2
plan superseding a v1 plan continues `plan_seq` (§3.2).

### 4.2 Transaction W-v3 — correction save

W-v3 runs `PUT .../tailoring/workspace` with a v3 body.
Compute recommendations and re-derive digests outside the
transaction. `BEGIN IMMEDIATE`:

1. Load job; 404 when missing. Compare workspace ETag (0
   creates); mismatch → 412 `WORKSPACE_CONFLICT`.
2. Recheck extraction/profile ownership and the active
   binding; v3 requires the CAPTURED binding (never the
   active pointer). `recommendationHash`, when present,
   must verify (as v1/v2).
3. Load the bound plan: must be the preparation's ACCEPTED
   plan with `schemaVersion step2-plan/v2` over the active
   extraction, with `planHash` recomputed. V1 accepted plan
   → 409 `PLAN_STALE` (the client rebinds after a v2 cycle;
   the stored draft is preserved). Extraction drift → 409
   `PLAN_STALE`.
4. Validate every op against the v2 plan plus recomputed
   captured evidence: known suggestion/bullet ids; usable
   suggestions only in `add`/suggestion-`replace`; known
   employment roles; op `roleId` inside the server-derived
   eligible set for its anchors (master-bullet ops in
   their own role; suggestion ops in an eligible role);
   `replace` XOR; `summaryOrigin` naming master or a plan
   angle. Any violation → 422 `INVALID_SELECTION` with a
   `draft.*` field path. Duplicate adds (same
   `suggestionId`+`roleId`) collapse to the existing
   `operationId`; repeated excludes are no-ops.
5. INSERT revision 1 or UPDATE WHERE revision=:observed
   SET revision=revision+1 with the `WorkspaceStoredV3`
   bytes. Preserve `last_request_id`/
   `last_submitted_revision`. Commit or roll back all. No
   job version increment, queue/review/provider call, or
   provenance write: the workspace stores operations only.

### 4.3 Transaction V-v2 — correction validation

V-v2 runs `POST .../tailoring/draft/validate` with a v2
body. Derive segments and verdicts outside the transaction;
persist inside one short transaction. `BEGIN IMMEDIATE`:

1. Load job (404), accepted v2 plan over the active
   extraction (409 `PLAN_STALE` otherwise), and the
   workspace at `body.workspaceRevision` (409
   `WORKSPACE_CONFLICT` on mismatch — same revision rule
   as v1 validate).
2. Re-verify the captured binding (evidence digest +
   payload hash); drift → 422 `PROFILE_NOT_READY`. JD
   presence → 422 `JD_NOT_READY` when unreadable.
3. Compute `correctionDraftHash` over the submitted bytes,
   derive segments (§7.4), run `validateCorrectionSegments`
   (§7.1), and INSERT the `step2_draft_validations` row
   (`policy_version step2-claims/2`). Structural failures
   are DATA in the persisted verdict, not HTTP errors:
   the endpoint returns 200 with `structural.ok=false`
   entries. Commit → 200 `ValidateDraftReplyV2`.

### 4.4 Transaction G-v2 — provenance-aware freeze and submit

G-v2 runs `POST .../tailoring/generations` when the stored
workspace holds v3 bytes. Request lookup FIRST (before any
other check): existing identical `submitHash` → 200 replay
with zero writes; different bytes same ID → 409
`IDEMPOTENCY_MISMATCH`. Then, outside any transaction
(Phase 0, read-only): resolve the frozen v3 draft —
workspace revision match, job CAS read, no live work,
pinned captured inputs, provider/evidence readiness,
parent eligibility, source-hash re-verification; derive
segments over the exact bytes; locate or compute the
covering v2 validation (§7.6); require `covered &&
allStructuralOk`, else 422 `INVALID_SELECTION`
(structural; names segments). Budget counts are advisory
and never reject. Build the provenance manifest (one
entry per included segment, §7.5) and the
`step2-edited-inputs/v2` bytes; reject over-64 KiB with
422 `BUDGET_EXCEEDED`.

Inside `BEGIN IMMEDIATE` (no I/O, no `await`): re-lookup
for raced commits (200 replay), recheck workspace
revision, job CAS, `REJECTED` guard, live-work guard;
create/reuse candidate/JD snapshots; insert work item →
generation request (v3 payload with
`step2-request-input/v2` hash) → immutable request inputs →
`step2_generation_inputs` (v2 edited inputs + v2 policies)
→ `step2_draft_validations` row when computed in-Phase-0;
CAS the job once to `PENDING`; CAS the workspace
revision+1 with `last_request_id`/
`last_submitted_revision`. REVISION also flips the parent
and appends the review atomically. Any failure aborts all,
including new snapshots. Commit → 202.

The v1 stored-workspace path keeps the S2-D G gate
byte-for-byte (blocking `needs-evidence` verdicts,
`UNRESOLVED_EVIDENCE`). Version discrimination is by the
stored bytes' `schemaVersion` — never by a client claim.

## 5. CAS, idempotency, and polling

- Workspace ETag keeps the exact B scheme
  `"tw:{jobId}:{revision}"` for v1, v2, and v3 bodies:
  absent → 428, malformed/wildcard/list → 400, wrong
  job/revision → 412 `WORKSPACE_CONFLICT`. The response
  carries the stored version's schema; clients branch on
  `schemaVersion`.
- Job CAS keeps `observedRowVersion` (409 `JOB_CONFLICT`),
  independent of workspace ETag. P/PR/G bump
  `jobs.row_version`; preparation state never moves board
  status; W never bumps the job version.
- G idempotency is (`requestId`, `submitHash`) as before:
  same-id/changed-bytes → 409 `IDEMPOTENCY_MISMATCH`;
  byte-identical replay → 200 with zero writes, including
  across the v1/v2 boundary (a replayed v1 operation id
  with v1 bytes still converges on the v1 request).
- Retry (R) is unchanged and version-agnostic: it requeues
  the frozen request bytes, whose embedded v1/v2 lineage
  decides execution. Retry never reads the live workspace.
- Polling reuses the Step 3 cadence: 2 s visible / 10 s
  hidden, stopping at terminal states. Browser clocks write
  nothing. Batch diagnostics poll the batch GET, never a
  mutation.

## 6. Worker lifecycle

### 6.1 PREPARE handler with v2 lineage

Registration, kinds, claim filtering, stale-lease recovery,
and the five stages are unchanged (§3.4; S2-A §6). New
cycles verify the binding exactly as v1 (payload schema →
ownership → `bindingHash` → active extraction → payload +
evidence digests → provider presence), then:

1. Emit `LOADING_INPUTS` after bound inputs verify.
2. Build `PreparationInputV2` (prompt `prepare-prompt/v2`)
   and emit `WAITING_FOR_PROVIDER`; call the provider
   through the existing command adapter (120 s timeout,
   64 KiB output cap). Parse strict
   `PreparationProposalV2`: schema failure →
   `INVALID_RESPONSE` (retryable within budget); extra
   trust fields fail here, before semantics.
3. Emit `VALIDATING_PROPOSAL`; run proposal validation
   (§7.2): quote verification, anchor validation,
   priority-link validation (same-plan, ≥1, unique),
   eligible-role derivation, usability rules. Whole-
   proposal rejection (no plan row, `INVALID_RESPONSE`)
   only for: schema failure, binding mismatch, zero
   priorities with a non-empty JD, every priority failing
   quote verification, or zero LINKED priorities (every
   angle/suggestion stripped of links).
4. Emit `STORING_PLAN`; insert the `step2_plans` row
   (`prompt_version prepare-prompt/v2`,
   `proposal_schema_version preparation-proposal/v2`,
   `claims_policy_version step2-claims/2`,
   `validation_json` as `PlanValidationV2`) with the next
   `plan_seq` and `supersedes_plan_id` naming the prior
   accepted plan (v1 or v2).
5. Flip the accepted pointer (forward-only, idempotent);
   emit `PUBLISHING_PLAN`; complete.

Crash recovery, caching (`source: "cached"` with all five
stages, "Loading the saved plan…"), bounded retry
(`maxAttempts = 3`, no exactly-once remote claim), and
exhaustion terminalization are unchanged. Renewal reuses
the F formula with one timer; failed renewal aborts
write-free. Every preparation write rechecks the
live-lease tuple in the same short transaction (S2-A §6.2
SQL, unchanged).

### 6.2 TAILOR execution of frozen v2 inputs

The worker reads ONLY the frozen rows (`generation_requests`
+ `tailoring_request_inputs` + `step2_generation_inputs`);
it never consults the mutable workspace revision, active
profile pointers, or provider-declared trust. Before any
render:

1. Recompute `correctionDraftHash`,
   `correctionManifestHash`, and `step2-request-input/v2`
   over the frozen bytes; mismatch → `INPUT_STALE`, no
   version, no approval effect.
2. Re-derive segments and re-run `validateCorrectionSegments`
   over the frozen draft; require `covered &&
   allStructuralOk`, else `CLAIM_VALIDATION` (structural) —
   provenance never blocks here either, and budget counts
   are advisory, never a refusal.
3. Verify each manifest entry's `textHash` equals the
   rendered segment's exact bytes; mismatch →
   `PUBLISH_FAILED` (fail closed, never silently rewrite).

Rendering applies Add/Replace/Exclude in op order with the
S2-D applier (per-bullet `sourceOperationId`, first-add/
replace role derivation, identical texts bound per bullet,
bullet counts advisory — rendered as-is, never trimmed);
user edits render verbatim. Publication attaches version/claims/artifacts/
assessment/active pointer/request success under the lease
plus input/job fences (unchanged F tuple plus the v2
hash fences above). Crash after publication recovers the
committed request/version without provider rerun;
analysis-only crashes reuse the validated immutable
proposal; cached paths emit real `cached` boundaries.
v1 frozen rows execute through the unchanged S2-D path.

## 7. Claim-validation policy `step2-claims/2`

Normative algorithm, implemented pure across
`src/domain/step2Correction.ts` (derivation, eligibility,
segment building) and
`src/tailoring/step2CorrectionPolicy.ts` (digests, quote
verification reuse, verdict computation). Two entry points
share the text rules: `verifyPlanQuotes` (reused unchanged
from v1 policy — UTF-8 byte ranges, never UTF-16 indices)
and `validateCorrectionSegments`.

### 7.1 Provenance derivation (exhaustive, ordered)

`deriveSegmentProvenance({origin, originText, text,
userEdited, originUsable, lineageIntact})`:

| # | Condition | Provenance |
|---|---|---|
| 1 | `claimKey(text) = claimKey(originText)`, not user-edited, lineage intact, origin is master summary/bullet | `VERIFIED_SOURCE` |
| 2 | same sameness/lineage, origin is angle/suggestion, origin usable | `USER_ACCEPTED_AI` |
| 3 | anything else — any saved text change, unusable origin, broken lineage | `USER_EDITED` |

`lineageIntact` means every anchor is approved and owned by
the bound profile version (master-summary segments pass
true when the captured binding verifies — activation is
their lineage). `originUsable` applies to suggestion
origins (plan `usable` flag); angles are always
selectable. An allowlisted derivation manifest (`derivation`
equality, same allowlist as /1) records `match:
"derivation"` for audit; it never converts user-authored
text into verified text.

Consequences, pinned by contract tests:

- Untouched master summary/bullets with intact lineage →
  `VERIFIED_SOURCE`; counts as machine-verified.
- Selected unchanged AI angles/suggestions → `USER_ACCEPTED_AI`;
  generatable; never counted as machine-verified.
- Any saved change — `editedText`, `edit` ops,
  `replace`-with-text, summary text differing from its
  origin, added metrics/technologies/responsibilities →
  `USER_EDITED`; generatable verbatim; never counted as
  machine-verified.
- Token overlap, a bare fact id, or a provider assertion
  alone can never produce `VERIFIED_SOURCE`: rule 1
  additionally requires normalized text equality with the
  origin. (R-ADR-026; S2CPA3.)
- `replace`-with-text always records authorship
  (`USER_EDITED`) even when the retype happens to equal
  the target bytes: the op declares authorship. `add`
  with `editedText` equal to the suggestion text, and
  `edit` ops that change nothing, are not edits.

### 7.2 Proposal validation (worker, plan accept)

Per-item checks before a v2 plan row is accepted (extends
S2-A §7.2; recorded in `PlanValidationV2`):

- Priorities: quote verification + `importance` preserved
  + support recomputed by `recomputePrioritySupport`
  (unchanged). Required-but-unsupported stays a visible
  `gap` — never padded, never promoted.
- Priority links: every angle/suggestion keeps only
  `priorityIds` that name priorities of THIS plan
  (recomputed ids after quote validation), unique,
  non-empty. Entries naming dropped/foreign ids are
  recorded in `droppedPriorityIds` with
  `FOREIGN_PRIORITY`/`PRIORITY_LINK_MISSING`. An angle or
  suggestion left with zero kept links is dropped (angle)
  or unusable (suggestion, `PRIORITY_LINK_MISSING`).
- Angles: `factIds` exist/approved/owned; the two angles
  textually distinct and distinct from keep-master
  (duplicates collapse, no padding).
- Suggestions: `roleId` names a payload employment;
  `factIds` exist/approved/owned by that role or
  transferable; no novel numbers versus cited statements
  +metrics; no company name outside the derived eligible
  employers (employer-swap → unusable `FOREIGN_EMPLOYER`);
  eligible set non-empty (mixed ownership → unusable
  `MIXED_OWNERSHIP`); provider `roleId` inside the
  eligible set (else unusable
  `PROVIDER_ROLE_INELIGIBLE`). Failures mark the
  suggestion `usable: false` — the plan still accepts. A
  plan with zero usable suggestions accepts (sparse
  case): the editor shows master bullets only.
- Whole-proposal rejection (no plan row,
  `INVALID_RESPONSE`) only for: schema failure, binding
  mismatch, zero priorities with a non-empty JD, every
  priority failing quote verification, or zero LINKED
  priorities.

Provider/model/prompt/proposal lineage columns bind
reproducibility to exact bytes, never to model identity.

### 7.3 Eligible-role derivation (server-side)

`deriveEligibleRoles({citedFactIds, employmentByFactId,
employmentIds})`:

- Any cited id unknown → `{ownership: "unknown",
  eligible: []}` (caller reports `INVALID_ANCHOR` first).
- No employment-owned cited facts → `{ownership:
  "transferable", eligible: all employments}`.
- All employment-owned cited facts share one employment
  E (which must be a payload employment) → `{ownership:
  "single", eligible: [E]}`.
- Otherwise (facts span employments, or name a
  non-payload employment) → `{ownership: "mixed",
  eligible: []}` — fails closed.

Enforced independently in plan acceptance (§7.2), plan
reads (`PlanReplyV2.eligibleRoles`, recomputed per read),
W-v3 saves (§4.2), and V-v2/G-v2 validation (§7.1 role
rule). The UI displays and accepts only eligible target
roles (§11); server refusal is authoritative.

### 7.4 Segment derivation (selected-summary-only anchors)

`deriveCorrectionSegments({plan, master, masterSummary,
summaryText, summaryOrigin, operations})`:

- One summary segment when `summaryText` is non-empty
  (empty summary = no segment, nothing to generate).
  Master origin: anchors `[]`, priorities `[]`
  (activation is the lineage). Angle origin: that
  angle's fact/priority ids ONLY. The v1 union of all
  unselected suggestion/angle facts is forbidden.
- `add`/`replace`-with-suggestion: one segment citing
  that suggestion's plan anchors/priorities.
- `replace`-with-text: one segment citing
  `[targetFactId]`, no priorities, always user-authored.
- `edit` on suggestion: one segment citing that
  suggestion's anchors/priorities, role from the first
  matching `add`/`replace`-with-suggestion instance.
- `edit` on bullet: one segment citing `[targetFactId]`
  with the bullet's role.
- `exclude`: no segment. Unknown plan references: no
  segment (W-v3 rejects them; generation fails closed).

V-v2, G-v2, and the worker share this function so
advisory verdicts, the gate, and execution can never
disagree on what text is included.

### 7.5 Provenance manifest and frozen binding

G-v2 builds one `Step2ProvenanceEntryV2` per included
segment: segment id, kind, role, origin, anchors,
priorities, exact/normalized hashes, server-derived
provenance, and `sourceOperationId` (the op whose text
renders; null for the summary and untouched master
rows). The manifest freezes inside
`step2-edited-inputs/v2`; `correctionManifestHash` binds
it into `step2-request-input/v2`. The worker verifies
manifest `textHash` values against rendered bytes before
publishing (§6.2). Manifests are never supplied by
clients and never merged with live workspace state.

### 7.6 Race handling and persisted verdicts

- Any edit changes `correctionDraftHash`; old verdict
  rows no longer match and are ignored (never applied to
  newer text). Late-arriving verdicts for a superseded
  hash are stored but inapplicable.
- G-v2 requires a covering v2 validation (same
  `segmentId` + exact-bytes `textHash` per segment via
  `verifyCorrectionCoverage`) with `allStructuralOk`;
  budget counts are advisory length guidance, never a
  gate. Direct API callers may skip the
  validate endpoint: G-v2 replays validation over the
  frozen inputs and persists the row in-txn on success;
  blocked attempts write nothing at all.
- Stale asynchronous verdicts cannot enable Generate:
  the G path recomputes hashes from frozen inputs and
  compares, never trusting a client-supplied validation
  id alone.
- `USER_EDITED` segments never block; `structural.ok =
  false` segments always block with named reasons.

### 7.7 Approved-wording chronology (carried forward)

S2-A §7.3 lineage proof stands: supporting text must
belong to the captured `profileVersionId` (created
before the plan); the plan's `created_at` must precede
submission; newer profile versions cannot support the
captured plan (explicit re-preparation only). A newly
approved fact lands in a newer version and stays
unusable for the captured draft. No hidden master
mutation exists in any path.

### 7.8 Evidence coverage (G interface)

`correctionVerifiedCoverage(validation)` partitions
segment ids into verified (`VERIFIED_SOURCE`) and
non-verified. G assessment denominators/numerators for
`evidence_integrity` count verified ids only; the
non-verified categories are reported as separate counts
(`provenanceCounts`) and never inflate either side.
Zero verified segments is `not_assessed`
(`NO_ELIGIBLE_ITEMS`), never `0%`. No composite
ATS/Overall score exists (R-ADR-024, unchanged).

### 7.9 Limitations (recorded, not waived)

`step2-claims/2` proves traceability, not semantics:
structural safeguards establish that AI text links
exact priorities, valid anchors, and eligible roles —
they do not assert entailment. `USER_EDITED` text is not
fact-checked (user authority). Technology/responsibility
novelty in AI proposals without new numbers or payload
company names still reports coarse diagnostics; the
usability verdict stays correct. Embeddings/KeyBERT/
Transformers.js remain out; any future semantic policy
ships as `step2-claims/3` and never reinterprets `/2`
verdicts.

## 8. Intake binding boundary

Unchanged from S2-A §8: capture at acceptance (default

## 9. Provider planning schema, prompt, and rewrite policy

Preparation reuses the existing provider stack only
(`scripts/ai-provider.mjs` dispatch, `TailoringProvider`
boundary, command adapter exit taxonomy). No KeyBERT,
Transformers.js, Python, or new dependency. S2-CP-B
extends `src/tailoring/contract.ts` with
`PreparationInputV2`/`PreparationProposalV2` (§1.7); the
pure `src/domain/step2Correction.ts` carries identical
Zod text so contract tests pin them first.

Prompt `prepare-prompt/v2` (normative content; S2-CP-B
stores the exact string as a checked-in constant and
records its hash in lineage):

1. Role: quote JD requirements exactly; propose resume
   angles and bullets grounded ONLY in the supplied
   approved facts.
2. Every priority quote must be a verbatim JD substring;
   supply byte offsets counted in UTF-8 from the JD
   start.
3. Rank by importance to the role (required first),
   independent of candidate support; mark support
   honestly — the grade is advisory, deterministic code
   recomputes it.
4. Every angle and suggestion MUST link the exact JD
   priorities it addresses by their supplied priority
   ids (≥1 each); never invent ids.
5. Angles and suggestions must cite the fact ids they
   rest on; never invent metrics, technologies,
   employers, dates, or responsibilities; never move
   experience across employers; propose the owning
   employer's role for employment-grounded text.
6. Prefer reusing fact/master wording verbatim.
7. Fewer than three priorities or zero suggestions is
   acceptable when evidence is sparse; never pad with
   boilerplate.
8. Output strict JSON matching
   `preparation-proposal/v2` only; no provenance,
   verification, acceptance, eligibility, scores, paths,
   or approval assertions. The server derives trust.

Grounded rewrite policy: provider wording is a proposal.
A suggestion becomes a usable plan item only through
§7.2 checks; it renders only when the user explicitly
selects it, as `USER_ACCEPTED_AI` — never as verified
fact. The provider cannot choose plan acceptance,
hashes, pointers, provenance, eligibility, or coverage.

### 11.1 The one Generate transition

Step 2 has exactly one primary action: **Generate resume**.
The S2-D `Continue` control — which flushes and navigates to
Step 3 WITHOUT submitting generation — is REMOVED (it let
users reach progress UI with no run behind it, forking the
exit vocabulary). The transition vocabulary is
`GENERATE_TRANSITION_STEPS = [flush, resolve, freeze,
submit, follow]`:

1. `flush`: PUT the current draft under workspace CAS; stop
   on 412/409 with retained input (no POST follows).
2. `resolve`: POST V-v2 over the exact saved bytes; stop on
   structural blocks with named segments (no POST
   follows). `USER_EDITED` never blocks, and length
   guidance never blocks.
3. `freeze`: server-side — the G-v2 freeze (§4.4) builds
   the manifest and immutable rows.
4. `submit`: POST G with the minted operation id; retain
   the exact body/id for uncertain-response replay.
5. `follow`: navigate to Step 3 ONLY after 202 or a
   byte-identical 200 replay.

Reads, mount, navigation, autosave, cancel, and failed/
conflicted saves insert zero generation rows (ΔQ1 = 0).
Identical uncertain-submit replay inserts no duplicate
(200 replay). S2-CP-C pins: one visible primary action,
no `Continue`-to-Step-3 control, and the ΔQ1 = 0 matrix.
