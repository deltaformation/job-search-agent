# v1.3 D — Step 1 and recommendations handoff for E (F, G)

WO-1.3-D interface publication (2026-09-16). The deterministic
recommendation adapter is live behind `GET .../recommendations`
and transaction W, Step 1 renders retained canonical JD bytes, and
Generate readiness is computed for E to enforce. This document is
the exact contract surface: signatures, error names, D
interpretations of §3.1 open points, budgets, and test evidence.
Normative behavior stays in `docs/tailoring-contracts-v1.3.md`.

## 1. What D built

- `src/domain/extraction.ts` (new): strict
  `StoredExtractionEnvelope`/`StoredExtractionFields` reader for
  `job-extraction-v1`; `parseStoredExtraction` fails closed on
  unknown versions. `JOB_EXTRACTION_VERSION` is defined here and
  re-exported by `src/extraction/types.ts` (domain purity: domain
  modules import zod + siblings only).
- `src/domain/atsKeywords.ts`: `atsKeywordCategory` — the fixed
  §3.1 category dictionary (Technical/Business/Other).
- `src/domain/canonical.ts`: `truncateCodePoints` — deterministic
  code-point-safe truncation for schema-bounded derived text.
- `src/tailoring/recommendations.ts` (new): pure
  `buildRecommendations(input)` over canonical JD + immutable
  payload + APPROVED facts. Reuses `extractAtsKeywords` (≤100,
  never padded) and `evaluateKeywordSupport`; converts extractor
  UTF-16 offsets to UTF-8 byte ranges and verifies the exact
  decoded slice (misaligned ranges drop the phrase, never emit a
  false citation). Output is `RecommendationV1.parse`d — fail
  closed.
- `src/server/recommendations.ts` (new): `getRecommendations`
  (GET path: ownership + active binding + build),
  `workspaceRecommendationsProvider` (W's adapter: ownership +
  build, no active checks — W rechecks active ownership inside
  its own transaction), and `getTailoringReadiness` (E's gate).
  Read-only throughout (ΔQ1=0, ΔQ9=0); no provider call anywhere
  on the read/edit path.
- `app/api/jobs/[id]/tailoring/recommendations/route.ts` (new):
  `GET ?extractionId=&profileVersionId=` → 200
  `RecommendationsReply`; 400 malformed/required UUIDs; 404
  ownership; 409 `INPUT_STALE` owned-not-active; 422
  `JD_NOT_READY` active binding without JD text; 503 corrupt
  storage. `Cache-Control: no-store`, ErrorBody failures.
- `app/api/jobs/[id]/tailoring/workspace/route.ts`: the pending
  provider is replaced by `workspaceRecommendationsProvider`.
  Complete bindings now build real snapshots: W saves require the
  fresh `recommendationHash`, and empty drafts still save with
  honest null snapshots when JD text is missing.
- `src/server/board.ts`: additive
  `ExtractionView.retainedDescriptionText` (canonical bytes behind
  strict validation, null when missing/corrupt — the module's
  fail-soft contract for board reads).
- `components/tailoring/TailoringWorkflowShell.tsx`: Step 1
  renders `retainedDescriptionText` with the denormalized job copy
  as fallback; salary/location stay exact-or-Unknown.

## 2. §3.1 open points D fixed (E/F/G rely on these)

- Categories: curated technical lexicon → `Technical`, curated
  business phrases → `Business`, backfill → `Other`. The
  extractor never emits a backfill token colliding with a curated
  entry, so the mapping is exact.
- Roles: IDs are the immutable payload employment keys; labels
  are `Role @ Company (start – end|present)` truncated to 200
  code points; fact IDs are the role's approved facts in
  code-point order (≤100, deterministic head).
- Themes: one per achievement category among approved facts, in
  first-appearance payload order (≤10); IDs/titles are the
  category verbatim. Every theme shares the default summary:
  canonical master `payload.summary` when present, else approved
  statements joined in fact-ID order (≤4000 code points).
- Preset: supported phrases with approved facts whose text fits
  the 128-char selection cap, in phrase order (≤20); each maps to
  the first payload-order role owning ≥1 support fact (phrases
  with no role-owned support stay selected but unmapped);
  `themeId` is the largest theme (first-appearance tiebreak) or
  null; guidance starts empty. The preset always passes
  `validateFocusSelection` against its own snapshot.
- `profileHash` = SHA256 over `canonicalJson` of the parsed
  stored payload (stable: payloads are immutable). `jdHash` =
  SHA256 over `canonicalText` of the retained envelope
  description — the same convention `getOrCreateJdSnapshot`
  uses, so no snapshot row is needed to agree.
- Phrase text over 512 chars is skipped (pathological tokenizer
  output, not citable); fact-ID lists cap at 100/20 by
  deterministic order. Sparse JDs yield empty phrase lists —
  never padded.
- A profile version with zero approved facts still builds (all
  phrases gap/uncertain, empty preset): support evaluation is
  total. `PROFILE_NOT_READY` is a Generate-readiness code only,
  never a GET failure.

## 3. E's feed: preset, readiness, binding flow

- Preset bytes: `RecommendationV1.preset` is a complete FocusV1.
  Step 2 copies it into the draft focus and saves via W (E1);
  D4 proves the stored snapshot preset byte-equals the served
  preset. Mappings carry role-owned approved fact IDs only.
- `getTailoringReadiness(handle, jobId, env, {extractionId,
  profileVersionId})` → `{ok:true}` or `{ok:false, failure:
  {error, detail}}` with `unknown-job | profile-not-ready |
  jd-not-ready | provider-not-ready | storage-unavailable`.
  Precedence: profile (bound version exists with ≥1 approved
  fact) → JD (bound extraction carries text) → provider (active
  provider's key env var non-blank; presence-only, never logged
  or transmitted). Null IDs are not-ready, not 404. Wire into G:
  `profile-not-ready` → 422 `PROFILE_NOT_READY`,
  `jd-not-ready` → 422 `JD_NOT_READY`, `provider-not-ready` →
  422 `PROVIDER_NOT_READY`, `storage-unavailable` → 503.
- Binding flow (§5 profile-dropdown row, UI is E's): resolve the
  exact active version → GET recommendations → PUT workspace with
  the changed binding, the fresh hash, preserved free guidance,
  cleared selections/mappings, and reset summary/theme. W
  rejects uncleared stale IDs with 422 `INVALID_SELECTION` and
  hash drift with 409 — D5 proves both plus the cleared save.
  Switching bindings never changes the global default profile.
- Step 2 controls stay E's (cloud/inspector local state,
  selection/theme/summary/mappings/guidance W saves, G
  dispatch). D added no Step 1 essay and no Step 2 UI.

## 4. Budgets and error vocabulary

- GET recommendations: ≤8 statements (5 worst case: job,
  extraction, version, active version, facts); proven beside
  200 history rows. No artifact bodies, tokens, paths, or raw
  JSON in responses; corrupt rows → typed 503, never unchecked
  data.
- Service errors: `unknown-job`, `not-found`, `input-stale`,
  `jd-not-ready`, `storage-unavailable` (+ `profile-not-ready`,
  `provider-not-ready` for readiness). W-adapter errors reuse
  B's vocabulary: `extraction-not-ready` (missing JD or, inside
  W's pre-checked flow, unreachable ownership drift),
  `storage-unavailable`.

## 6. First product-testing checkpoint

Per WO-1.3-D's exit line: **board, shell, Properties/Notes, and
actual input data.** A tester on a capable machine (real browser;
this sandbox cannot launch Chromium) can now:

1. Open the board, activate a card, and land on
   `/jobs/[id]/tailor` with the four-step shell.
2. Open Properties/Notes and confirm exact persisted metadata
   and working notes.
3. Read Step 1's retained JD, salary, and metadata (Unknowns
   stay Unknown), then Continue to Step 2's honest placeholder.
4. Call `GET .../recommendations` for the active binding and
   confirm byte-stable phrases, support, roles, themes, and the
   preset — with no provider key configured.

Step 2 controls, Generate dispatch, worker progress, and review
stay honestly disabled until E–G land. Known environment limit:
browser/PDF legs need a capable machine or CI.
