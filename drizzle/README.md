# SQLite migrations

Ordered, checked-in SQL migrations for the product database. The custom runner
(`src/db/migrate.ts`) applies every top-level `*.sql` file in lexical filename
order inside one transaction per file, records each filename plus its SHA-256
in `_schema_migrations`, and refuses to start when a previously applied file
changed on disk.

## Current baseline

- `0000_*.sql` — generated by `npm run db:generate` from `src/db/schema.ts`.
  Never hand-edit this file; regenerate it from the Drizzle schema instead.
- `0001_trigger_guards.sql` — hand-reviewed companion with trigger guards and
  one partial unique index that Drizzle cannot express. Edit only with a new
  reviewed migration file, never by rewriting history.
- `0002_candidate_snapshot_dedupe.sql` — hand-reviewed unique index that IS
  expressed in `src/db/schema/candidates.ts` (`candidate_snapshots_version_hash`).
  The next `db:generate` diff will re-emit it (the kit journal predates it);
  drop that statement from the generated file when merging.

## Ordering rule

After adding `0001` by hand, the next `db:generate` output will also be named
`0001_*`. Rename the generated file to the next free sequence number (`0002_*`,
then update `drizzle/meta/_journal.json` to match) before committing, so
lexical order always equals apply order.

## Conventions

- New migrations are additive. Fix a bad migration with a newer migration, not
  by editing an applied file (the runner treats edits as drift and aborts).
- Table and column changes go through the Drizzle schema first, then generate.
- Trigger/index-only changes are authored directly as a new `NNNN_*.sql` file.
